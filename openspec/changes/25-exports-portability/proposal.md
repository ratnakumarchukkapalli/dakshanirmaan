# 25 — exports-portability (the books can always walk out)

Skill: daksh-api (route handlers, exceljs, auth gates) + daksh-ui (the Export screen) · daksh-schema only if a DB helper turns out to be needed. Model: Sonnet to build, Opus to review (owner-only data leaving the system; data integrity of the export).
Spec sections: openspec/specs/security-deployment/spec.md → "Business continuity" (the CA-friendly, Tally-independent exports paragraph) and the FY-close bullet; openspec/specs/api-architecture/spec.md → route handlers (`GET /api/backup/books.xlsx` admin full-books workbook; `GET /api/reports/tally.xml?fy=` voucher export), "Excel exports" (exceljs streaming, numbers as numbers with `numFmt`, dates as dates, never pre-formatted strings) and the report-export conventions (change 15: owner-only 403, row caps then 422).
Context: this app exists to replace Tally, so the owner must never be locked in. Three ways out: (A) a full-books Excel workbook, (B) a Tally XML voucher file for the case the business is ever forced onto Tally (CA insistence, sale of the business), (C) a self-contained financial-year archive kept offline that is readable with no app at all. All three are **owner-only (admin at aal2)** and read-only: nothing is posted, nothing changes.
Do not: use the `xlsx` package (banned: `exceljs` only); write to any ledger; use floats for money (read NUMERIC as strings and write them with exceljs as numbers parsed from the decimal text only at the last step, or as decimals strings with a numeric cell formatted — see Excel conventions in the spec); include secrets (no keys, no auth.users, no password hashes, no TOTP factors, no signed URLs, no Storage object contents); let a counter user, an owner below aal2, or a signed-out visitor reach any export.

## Scope

### A. Full-books workbook — `GET /api/backup/books.xlsx?fy=YYYY` (FY start year; default current FY)
One `.xlsx`, streamed (exceljs `stream.xlsx.WorkbookWriter`, rows read from the database in pages of 1,000 through the signed-in owner's user-scoped Supabase client, so RLS applies; never the service key). Sheets, each with a frozen header row, filters, real numeric/date cells, column widths, and a README sheet first (what each sheet is, FY, generated-at in org timezone, "as of" timestamp, row counts, and the trial-balance check):
1. **README**; 2. **Chart of accounts** (code, name, type, system key, active); 3. **Trial balance** at FY end (debit, credit, with a check row Σdr = Σcr); 4. **Journal** (one row per journal line: entry no, date, source type, source doc no, narration, account code/name, party, debit, credit, posted by, reversed flag); 5. **Party ledger** (all parties, opening/closing balance and FY movement) and **Parties** master (name, type, GSTIN, state, phone, address); 6. **Sales invoices** + **Sales invoice lines** (header totals and tax split; lines with the snapshotted item name, HSN, GST rate, qty, rate, discount, taxable, tax); 7. **Purchase invoices** + lines (incl. ITC flag, RCM freight); 8. **Credit notes / Debit notes** (+ lines); 9. **Payments** (receipts and payments with mode, reference, cheque status, discount) and **Allocations**; 10. **Cash deposits**; 11. **Expense vouchers**; 12. **Stock movements** (item, warehouse, qty in/out, rate, value) and **Stock on hand** at FY end; 13. **Items** and **Warehouses** masters; 14. **GST**: month-wise output and input tax summary and the GSTR-1 HSN summary if cheaply available from existing RPCs (`gstr1_data`, `gstr3b_summary`), otherwise skip with a note in README; 15. **Day closes** and **Bank statement lines** with match status (owner data).
Cancelled documents and their reversals are INCLUDED and flagged (status column), exactly as the books hold them. Row cap 200,000 per sheet then HTTP 422 with a plain message. All text cells are written as strings (never formulas); additionally prefix any text cell starting with `=`, `+`, `-`, `@`, tab or CR with an apostrophe-safe guard (a leading `'` or a zero-width-free escape — pick one, test it) to defuse spreadsheet formula injection from party names/narrations.

### B. Tally XML — `GET /api/reports/tally.xml?fy=YYYY` (+ optional `&company=` name, default the org's legal name)
Research first (see the research task below), then build an **accounting-mode voucher import** for Tally Prime/ERP 9: `ENVELOPE → HEADER (TALLYREQUEST Import Data) → BODY → IMPORTDATA → REQUESTDESC (REPORTNAME All Masters / Vouchers, STATICVARIABLES SVCURRENTCOMPANY) → REQUESTDATA → TALLYMESSAGE` with (1) ledger masters (each chart account and each party as a ledger under a sensible parent group: Sundry Debtors / Sundry Creditors / Bank Accounts / Cash-in-Hand / Duties & Taxes / Sales Accounts / Purchase Accounts / Direct & Indirect Expenses / Indirect Incomes, with opening balance 0 — the opening balances come as an opening journal voucher so the trial balance reproduces), and (2) every posted, non-reversed-pair journal entry of the FY as a voucher, type mapped from `source_type` (sales_invoice → Sales, purchase_invoice → Purchase, credit_note → Credit Note, debit_note → Debit Note, payment direction receipt → Receipt / payment → Payment, cash_deposit & everything else → Journal), voucher number = the document number, date `YYYYMMDD`, narration, and one `ALLLEDGERENTRIES.LIST` per journal line with the correct debit/credit sign convention (confirm it from the primary source: Tally's `ISDEBIT` / negative-amount rule) and `ISDEEMEDPOSITIVE`. Stock items are NOT exported (accounting-invoice mode only; the Stock sheet of the workbook carries quantities); say so in the README of the archive and on the screen. Rules: every voucher must balance to the paisa (Σ debit = Σ credit) or the export aborts with a clear error naming the entry; XML is built with proper escaping (names/narrations contain `&`, `<`, quotes, Telugu, emoji), UTF-16/UTF-8 as Tally expects (confirm), no control characters; amounts with exactly two decimals; reversed entries and their reversals are both exported (Tally's trial balance then nets them) so totals match the app's trial balance. Self-checks in the handler/tests: well-formedness, Σ per voucher, Σ over the FY equals the app's trial balance per ledger.
**Honest limit:** we have no Tally to test against. The README/screen text must say "generated to Tally's documented import format; not yet imported into a live Tally — have your CA test-import on a copy company first".

### C. FY archive — `GET /api/backup/archive.zip?fy=YYYY` (streamed ZIP)
A self-contained folder readable with no app at all: `README.txt` (plain English: what is in here, how to read it, FY, generated-at, app version, the as-of timestamp, who generated it), `books.xlsx` (A), `tally.xml` (B), `data/*.json` (one JSON file per table/view above, full snapshots, money as decimal strings, dates ISO, plus `schema.json` describing each file's columns) , `reports/*.pdf` (react-pdf, same stack as invoices: trial balance, profit & loss, balance sheet, receivables ageing as at FY end, stock valuation as at FY end, GST summary — a small generic tabular report PDF component is enough, no new design), `gst/` (GSTR-1 portal JSON per month if the existing exporter can produce it for the FY, else omit and say so in README), `MANIFEST.sha256` (SHA-256 of every file, so tampering or corruption is detectable) . Invoice PDFs are NOT bundled (rendering thousands inside a serverless request is not safe); the invoice JSON/Excel carries every field and any single invoice PDF is one click from the app — say so in the README. Use a small, well-known, dependency-free streaming zip library (suggest `fflate`); add it as an exact-version dependency, justify it in the notes (no install scripts, no transitive deps, `npm audit` clean), and do not write to disk (stream to the response). If streaming cannot finish inside the platform's function time limit for realistic sizes (a year of a family trading business: ≤ 10,000 documents), say so in the notes with measured timings from the local demo data scaled up, and set `maxDuration` appropriately; fall back to documenting that very large years should be exported per quarter.

### D. Export screen — Settings → "Export & backup" (owner only; same guard as the other owner-only settings tabs)
Pick the financial year (default current), three buttons: **Full books (Excel)**, **Tally file (XML)**, **Year archive (ZIP)**, each with one plain sentence of what it contains and the Tally honesty note; a line "Last nightly database backup: ..." only if that information already exists somewhere cheap to read (otherwise omit). en + te strings, 390 px, both themes. Each download is audited: add an `audit_log` row (`action 'export'`, entity name, FY) — via an existing audit mechanism if one fits (e.g. an RPC that a user-scoped call can use); if none exists, write a tiny SECURITY DEFINER `log_export(p_kind text, p_fy int)` (owner/aal2 only, pinned search_path, revoked from public/anon/service_role, pgTAP in the next test number, catalog guard 00026 stays green) — this is the only DB work in this change.

## Research task first (Tally)
Before writing the Tally exporter, fetch Tally's PRIMARY documentation (TallyHelp / Tally Developer / "Integration with Tally" XML import reference) and write `docs/research/tally-xml-format.md` (same style as `docs/research/hdfc-statement-format.md`: source tags, UNVERIFIED markers): envelope shape, ledger master message, voucher message fields, debit/credit sign rule, date format, voucher type names, how an opening balance is imported, encoding, which fields are mandatory, what happens on duplicate masters, and known import errors. The exporter follows that file.

## Conservative defaults (log in implementation-notes.md)
1. Owner-only everywhere (admin at aal2); a counter or aal1 owner gets 403 and zero database reads.
2. "As of" consistency: take `now()` once at the start and filter every table by `created_at <= as_of`; posted rows are immutable so the export is internally consistent (state this in README).
3. No stock items in Tally; no attachments/bill photos in any export; no auth data.
4. FY = the org's April–March year; selectable years come from existing `fiscal_periods`.
5. Reversed entries are exported with their reversals, flagged, never silently dropped.
