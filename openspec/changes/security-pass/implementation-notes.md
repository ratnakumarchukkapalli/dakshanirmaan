## Application security fixes

Findings T1 (app part), P1, A1 (UI), A3 to A8 of `docs/reviews/2026-10-final-security-pass.md`. Gates: `tsc` clean, lint 0 errors (29 pre-existing warnings, all in `scripts/attack-test/*.mjs`), vitest 88 files / 1089 tests, `npm run build` green.

- **T1 cookies:** `src/lib/supabase/cookie-options.ts` (`secure` only when `NODE_ENV === 'production'`, `maxAge` 8 h, `sameSite` lax, path `/`) is passed to all three clients (server, proxy, browser). Consequence: a production build (`next start`) served over plain http will not keep the sign-in cookie; test production builds over https or `localhost` via a browser that treats it as secure (Chrome/Firefox do for `localhost`, Safari does not).
- **P1:** `changePassword` takes `currentPassword`. It is checked with `signInWithPassword` on `createStatelessClient()` (`src/lib/supabase/stateless.ts`, no cookies or storage) before `updateUser`; the probe's own session is ended; then `signOut({ scope: 'others' })` (failure there returns `partial`, password already changed). Wrong password: friendly `validation` (`errors.validation.current_password_wrong`, en+te), with the sign-in limiter. Owner minimum 12 characters (`changePasswordSchemaFor(role)`; also applied to inviting an owner and to resetting an owner's password); counter staff keep 8. The account form has the new field.
- **A4:** the sign-in limiter counts failures only (`signInAllowed` / `recordSignInFailure` / `recordSignInSuccess`). Per (email, address) 10 failures / 15 min, per address 30 failures / hour, per email (any address) 100 failures / 15 min. A success clears the pair and remembers it ("known") for 30 days; a known pair ignores the per-address and per-email ceilings and only its own 10-failure budget applies. Deliberate deviation: an unknown address that is under its own budget is still blocked while the per-email backstop (100 failures in 15 min, i.e. a distributed attack) is tripped; the owner then signs in from a known address. `allowCodeCheck` (old, all-attempts counting) is removed; `allowCodeRequest` (unused magic-link limiter) is untouched.
- **A1 UI:** Settings -> Users shows "Authenticator set up: yes/no" (chip, en+te) per ACTIVE owner from `owner_totp_status()` via `loadUserRows` in `src/lib/users-data.ts`; any RPC error, a missing function or an odd answer yields null and the chip is not shown (never a false "no"). Requires the database function from the other half of this pass.
- **A3:** `decideAccess` decodes the path (`canonicalPath`: `decodeURIComponent` + collapses `//`); a malformed escape redirects to `/` (signed in) or `/login`. Every settings sub-page now starts with `requireOwnerPage()` (users page too), pinned by a source test (`settings/pages-gated.test.ts`) that fails when a new settings page lacks it. Matcher dots escaped (`favicon\.ico`, `sw\.js`, `offline\.html`), with a test.
- **A5:** `src/lib/invoice-pdf/link-limits.ts`: every signed-link request counts per address (30 / 10 min); every correctly signed request counts per invoice (30 / 10 min); 429 with `Retry-After: 600`; bad signatures keep their own 20 / 10 min budget. The per-invoice count runs after the signature check on purpose, so a stranger who only knows an invoice id cannot burn its budget. Signed link to a cancelled invoice: 410 (a signed-in member still gets the PDF). RUNBOOK section 3 notes the 410 and the limits (secret rotation revocation was already written there).
- **A6:** `Sec-Fetch-Site` check (`crossSiteRefusal` in `src/lib/export/guard.ts`) runs first inside `requireExportOwner`, hence inside `openExport`, so a cross-site or same-site request is a 403 before the session, any DB read or the `log_export` audit row. `same-origin`, `none` and an absent header pass. The three routes pass `request.headers.get('sec-fetch-site')` into their handlers. `recordExport` needed no separate check: every export route calls `openExport` before it.
- **A7:** `noControlChars` / `noControlCharsExceptBreaks` in `src/schemas/common.ts` (error key `text_invalid`, en+te) on party name, site label, address line 1 and city, `optionalText` (line 2, district, notes, transporter name, references; single-line by default), payment instrument/bank/note, purchase note, staff name/note, user name, item name, organisation legal name and every cancel/adjust `reason`. Only the quotation note (a textarea) allows tab and newline. Bank-statement narrations parsed from an uploaded file are NOT rejected (that would refuse a whole import); they are cleaned on the way out. `safeText` moved to `src/lib/safe-text.ts` (re-exported from `export/xlsx.ts`) with `safeCells`; every `addRow` in `reports/xlsx.ts`, `reports/xlsx-books.ts` and `statement/xlsx.ts` goes through it, and the workbook creator is stripped of XML-illegal characters.
- **A8:** `inviteUser` on the `email_exists` branch (only after the "already a member" check, so a real member is never touched): `updateUserById(userId, { password, ban_duration: 'none' })`, then lists and deletes every MFA factor via `auth.admin.mfa.listFactors/deleteFactor` (supabase-js 2.117), each error is logged and returned as a friendly `internal`. `scripts/create-admin.mjs` now exits 1 when its `updateUserById` fails. The shared test harness got an `admin.mfa.*` stub.
- **Not done / notes:** no browser walk; `supabase/` and `scripts/backup`, `.github` untouched; the attack-test harness was not run. ## Database fixes

Findings D1, T1, S1, A1 (DB part), A2, D2, D3. Migration `supabase/migrations/20261011100000_security_pass.sql`; pgTAP `supabase/tests/database/00039_security_pass.test.sql` (142 tests). Full suite on a fresh `supabase db reset`: 39 files, 3068 tests, PASS. Changed functions are their current definition (taken with `pg_get_functiondef` from a database built from the migrations) plus only the marked "Security pass" lines; the patches were applied by script with an exactly-one-match assertion and the diffs reviewed.

- **D1 lines:** `document_lines_guard(header_col, header_table)` BEFORE INSERT/UPDATE/DELETE on sales_invoice_lines, purchase_invoice_lines, delivery_challan_lines, expense_voucher_lines, stock_adjustment_lines, stock_transfer_lines (catalog sweep: these plus the already-guarded credit/debit note lines, quotation_lines and opening_lines are every child of a status-bearing header). Same rule as `note_lines_guard`: header locked FOR SHARE, `DN_NOT_DRAFT` unless it is a draft, old and new header both checked on UPDATE, a vanished header (draft-delete cascade) lets lines go. No writer exemption was needed: every definer that writes lines (`_post_sales_invoice`, `post_purchase_invoice`, `post_delivery_challan`, `post_stock_adjustment`, `post_stock_transfer` snapshot/tax refresh; `convert_quotation_to_invoice`, `post_bank_expense` into a draft they just created) does so before its own `status = 'posted'` update. `opening_lines_guard` got the same FOR SHARE (and became SECURITY DEFINER, since FOR SHARE needs UPDATE on opening_batches which the client lacks); quotation_lines left alone (no client DML, `save_quotation` only).
- **Lock order / deadlock:** posting functions lock the header FOR UPDATE as their first lock; the line writer's first lock is the header FOR SHARE, so the waits are one-directional. Allocation side: `check_payment_allocation` and the new `payment_allocations_guard` both take the payment FOR UPDATE (same strength, so no share-to-update upgrade deadlock).
- **D1 allocations:** `check_payment_allocation` additionally raises `DN_NOT_DRAFT` when the payment is not a draft (`post_cash_sale` allocates while its receipt is a draft, verified). New `payment_allocations_guard` (BEFORE UPDATE/DELETE, OLD side): non-draft payment -> `DN_NOT_DRAFT`, except a DELETE while the transaction-local GUC `dn.release_allocations` equals that payment id, set/cleared around the DELETE in `bounce_cheque` and `cancel_document('payment')` (the only two paths that removed allocations of a posted payment). Clients cannot set it (no free SQL via PostgREST; no exposed function passes caller input to `set_config`).
- **Race proof (two psql sessions, scratch script, local stack):** Race 1: owner runs `post_sales_invoice` and holds the transaction 3 s; counter inserts a line 1 s later. Guard OFF (pre-fix): the insert waits, then lands -> `status=posted lines=2 line_taxable=2400 posted_taxable=400 journal_revenue=400` (the hole). Guard ON: the insert waits until the post commits, then `ERROR: DN_NOT_DRAFT` -> `lines=1 posted_taxable=400 journal_revenue=400`. Race 2 (counter inserts and holds 3 s, owner posts 1 s later): the post waits for the counter's commit and books both lines (`posted_taxable=2400 journal_revenue=2400`), guard on or off. No deadlock in either order.
- **S1 headers:** `posted_document_guard` as trigger `zz_posted_document_guard` (runs after the other BEFORE triggers) on sales/purchase invoices, credit/debit notes, payments, expense vouchers, delivery challans, stock adjustments, stock transfers, cash deposits, day closes, opening batches. Non-draft rows: DELETE refused; UPDATE allowed only for posted->cancelled (and transfer in_transit->received/cancelled), a cancel only after the document's journal entry has `reversed_by`, plus (only while posted/in transit) payments' cheque columns, sales invoices' e-way-bill/transport columns, transfer `received_at/by`, credit note `buyer_gstin` = its invoice's, day close `journal_entry_id` null -> its own entry, challan `invoice_id` -> the posted invoice made from it / null once that invoice is cancelled, and `updated_at`. Enumerated from every UPDATE on these tables in the current function bodies. Not allowed: `irn*`/`signed_qr` (no writer exists yet; e-invoicing will need this list extended). quotations not covered (no ledger effect, `quotations_guard` already freezes converted quotes).
- **S1 grants:** service_role keeps SELECT on all tables and INSERT/UPDATE/DELETE on `app_users` only (callers checked: `actions/admin.ts` reads app_users + auth admin API, `create-admin.mjs` upserts app_users, PDF link route reads, attack-test setup/cleanup upsert/patch app_users + auth admin; fixtures use psql as postgres). TRUNCATE/REFERENCES/TRIGGER/MAINTAIN revoked from service_role and REFERENCES/TRIGGER/MAINTAIN from authenticated on every public table; `alter default privileges for role postgres in schema public` revokes the same for future tables. Harness impact: none expected for service_role. Behaviour change the harness may record: a counter INSERT of a line/allocation under a posted header now fails with `DN_NOT_DRAFT` (P0001) instead of an RLS 42501 (BEFORE triggers run before the WITH CHECK policy) — still refused; update the expectation if a row compares the code.
- **T1:** `current_app_role()` also requires the earliest `amr[].timestamp` to be within 8 h. Decision on a token WITHOUT `amr`: not time-boxed. Every Supabase Auth access token carries `amr`; a token lacking it can only be minted by someone holding the JWT secret, who could equally mint a fresh timestamp, so this opens nothing, and it keeps the 38 existing test files' fabricated claims working without edits. Fail closed for `amr` present but empty, JSON null, not an array, or without a numeric timestamp. Same rule as `src/lib/auth/session-age.ts` (which is stricter: missing amr = expired in the app). Applies to counters too (8-hour shift). Everything that gates on the role (is_active_member, every policy, every definer) inherits it.
