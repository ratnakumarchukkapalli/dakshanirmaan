## Decisions (conservative defaults, owner can overrule)
1. **Purchases are owner-only end to end.** The database already lets only an owner post/cancel; supplier rates and input tax are not counter data. Actions use `requireAdminMember` (drafts too), the proxy redirects a counter session off `/purchases/**`, and the nav hides it. Tests in `access.test.ts`, `nav.test.ts`, `purchases.test.ts`. **Closed in 21b (database half):** RLS used to let a counter session insert/edit *draft* purchase rows through the API (policy `insert_draft ... is_active_member()`); they cannot post. Same accepted class as attack-test K1–K4; tightening it to admin belongs with a DB change reviewed by Opus.
2. **Supplier's bill number and date are required** on the screen (the DB columns are nullable: opening rows and older data stay valid). The supplier's bill may not be dated after the day it was received.
3. **Duplicate check in two places**: early, friendly (`billNumberTaken`, posted bills of the same supplier, case-insensitive) on save and post; the unique index is the guard for races. Drafts may repeat a number until one is posted.
4. **Item picker offers stock items only** (`post_purchase_invoice` refuses `non_stock_line`); the server checks it too.
5. **`rcm` is never sent from the form** (`rcm: false` on every save; the DB refuses `rcm = true` with `rcm_purchase_unsupported`). RCM freight is 21b.
6. **`taxable_value: 0` on draft lines** — the purchase-lines column is NOT NULL with no default (sales lines got a default in change 03); the posting function overwrites it. No migration for that.
7. Cancelling a bill whose goods were sold gets its own sentence pointing at a debit note (the generic negative-stock text says "reduce the quantity", which is wrong here).
8. List tiles: payable = Σ `v_open_purchase_invoices.open_amount` via `completeRows` (a list cut short by `max_rows` throws instead of showing a wrong total); ITC and RCM payable from the owner-only `v_trial_balance` ledgers. "Rebate accrued" tile waits for change 24.

## 21b database half (Opus, 2026-10-01)

Migration `20261004100000_purchase_attachments_and_address_guard.sql` (sections 1–3; section 4 is change 27b). pgTAP `00029_purchase_attachments.test.sql` (75 tests). Local only, not committed, not pushed. Items 2–4 (`attachments.ts`, UI, RCM freight block) are the app session.

### What the app code needs

- **Purchase drafts are owner-only in the DB.** Policies `insert_draft` / `update_draft` / `delete_draft` on `purchase_invoices` and `purchase_invoice_lines` = `is_active_member() and current_app_role() = 'admin'` + the draft conditions. A counter write now gets `42501` on INSERT and 0 rows on UPDATE/DELETE. Fixtures checked first: no pgTAP file, `supabase/demo/demo-data.sql` (acts as the aal2 owner) or `scripts/` fixture drafted purchases as a counter user — nothing needed changing. `scripts/attack-test/matrix.mjs` now expects counter purchase-draft writes to be refused.
- **Table `public.attachments`**: `id uuid`, `entity text` (only `'purchase_invoice'`), `entity_id uuid` (the bill id), `storage_path text unique`, `mime text` (`image/jpeg` | `image/png` | `application/pdf`), `bytes int` (1…5242880), `uploaded_by uuid` (set by the DB from the session — do not send), `uploaded_at timestamptz` (set by the DB), `created_at`. RLS policies `select_owner`, `insert_owner`, `delete_owner` (admin at aal2); no UPDATE (grant or policy).
- **Path shape** (CHECK + Storage policy): `purchase_invoice/<bill id>/<uuid>.<ext>`, lower-case uuids, `ext` = `jpg` for `image/jpeg`, `png`, `pdf` — it must match `mime`. Never use the client's file name.
- **Bucket** `docs`: private, `file_size_limit` 5242880, `allowed_mime_types` jpeg/png/pdf, created by the migration. Storage refuses wrong type (`mime type … is not supported`) and oversize (`The object exceeded the maximum allowed size`) even for the owner.
- **Storage policies** (`storage.objects`, `TO authenticated`): `docs_owner_select`, `docs_owner_insert`, `docs_owner_delete`, each `bucket_id = 'docs' and public.docs_object_ok(name, '<op>')`. True only for an owner at aal2, the exact path shape, and an existing bill; upload refused for a cancelled bill; delete refused while the bill is posted. **No UPDATE policy**: upload with `upsert: false`; an overwrite/move is refused. Counter, aal1 owner, deactivated user, anon: no list, download, signed URL, upload or delete. Verified through the real Storage API by the harness (upload, download, signed read URL, list, upsert, PUT, delete) as well as in pgTAP.
- **Order of operations:** upload the file first (signed upload URL or direct upload with the owner's session), then insert the `attachments` row — the row insert checks the file is already in `docs`. Delete: delete the row first (it carries the posted-bill check with a clear error), then the object.
- **DB error codes the app will see** (all `P0001`, message `DN_VALIDATION:<code>`):
  - `attachment_object_missing` — no object at `storage_path` in `docs` (upload not finished / wrong path).
  - `attachment_object_mismatch` — Storage recorded a different size or content type than the row declares.
  - `attachment_entity_missing` — the bill does not exist.
  - `attachment_entity_cancelled` — attaching to a cancelled bill.
  - `attachment_bill_posted` — deleting an attachment of a POSTED bill.
  - `attachment_immutable` — any UPDATE of a row (only reachable by service role / owner; sessions have no UPDATE grant → `42501`).
  - `bill_has_attachments` — deleting a DRAFT bill that still has attachments (remove photos first).
  - CHECK violations `23514` (`attachments_mime_check`, `attachments_bytes_check`, `attachments_storage_path_check`, `attachments_entity_check`), unique `23505` (`attachments_storage_path_key`), RLS `42501`.
  - Storage API refusals come back as HTTP 400 with `new row violates row-level security policy` (upload) or simply nothing deleted / not found (read, delete) — check the result, not only the status.

### Decisions (spec silent → conservative, logged)

1. **(Changed after the independent review, 2026-10-01: refused for a posted OR cancelled bill; only a draft's photos can be removed — a cancelled bill keeps its number and history, and its photo explains it.)** Original: **Deleting a posted bill's attachment: refused** (row: trigger `attachment_bill_posted`; file: `docs_owner_delete` policy) — it is audit evidence for input-tax credit. Allowed while the bill is a draft, and again once the bill is cancelled. Enforced in the DB for app sessions; the database owner (no `auth.uid()`, e.g. a maintenance job) can still delete rows by hand.
2. **Adding a photo to a posted bill is allowed** (evidence often arrives after posting); to a cancelled bill it is refused.
3. **A draft bill with photos cannot be deleted** (`bill_has_attachments`) rather than cascading: a cascade would orphan the files in Storage. The app's delete-draft action must remove the photos (rows + objects) first.
4. **The row insert verifies the stored object** (exists; size and type equal to what Storage recorded in `metadata.size` / `metadata.mimetype`, when present) — the brief put this re-check in the action; it is now enforced in the DB too, so the action's check is a friendly early message.
5. `uploaded_by` uses the table's own stamping trigger (`attachments_guard`), not `set_created_by` (that function writes `created_by`, which this table does not have; the 00026 guard checks only tables with a `created_by` column).
6. `docs_object_ok(text, text)` is a plain (invoker) function in `public`, executable by `authenticated` and `service_role`, not by `anon`/PUBLIC (00026 stays green). It only answers "may I" for the caller and reveals nothing beyond what the owner can already read.
7. No `audit_log` row for attachment add/remove (not a books event); `uploaded_by` / `uploaded_at` are the trail. Say if removals should be audited.

### Hosted (Supabase Free) — what may differ from local

- Local `postgres` (non-superuser) could create policies on `storage.objects` and insert into `storage.buckets`; this is the documented Supabase way and should behave the same on hosted via `supabase db push`, but it has not been run there.
- `attachments_guard` (SECURITY DEFINER, owner `postgres`) reads `storage.objects`; locally `postgres` has SELECT there and `BYPASSRLS`. If hosted ever differs, the row insert would fail with `attachment_object_missing` for every upload — check the first real upload after push.
- The size/type cross-check relies on Storage writing `metadata.size` / `metadata.mimetype` (it does locally, CLI v2.117). If a Storage version stops writing them, the check is skipped, not failed.
- Storage refuses a SQL `DELETE` on `storage.objects` unless `storage.allow_delete_query = 'true'` (its own guard); the Storage API sets it. App code must delete files through the Storage API, never SQL.
- Hosted Storage must also enforce the bucket's `file_size_limit` against the project's global upload limit (Free: 50 MB) — 5 MB is below it.
