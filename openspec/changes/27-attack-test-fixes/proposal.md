## Scope (one new migration + one new pgTAP file, next free numbers)

1. **F2 — `place_of_supply` is client-steerable (medium).** A counter user can `PATCH sales_invoices {"place_of_supply":"36"}` on a draft and post: an in-state customer is taxed IGST, an inter-state customer CGST+SGST, and `'99'` (no such state) is accepted. Fix in the database: at post time (`_post_sales_invoice`, copy the body exactly, change only this) and by a trigger on draft writes, `place_of_supply` must be a valid GST state code and must equal the delivery state — `shipping_address->>'state_code'` when a shipping address is present, else the party's `state_code`. Raise `DN_VALIDATION:place_of_supply`. Check the app writes it that way today (`src/app/actions/sales.ts`, `challans.ts` convert) so nothing legitimate breaks; if the app can legitimately send a different value, stop and ask. Conservative defaults to log: the shipping address itself stays editable by the counter (choosing the delivery site is a real-world fact); a state-code allow-list of 01–38 and 97; export/`96` stays unsupported (GSTR-1 already blocks it).
2. **F1 — allocations of a posted receipt are editable by the counter (medium).** RLS on `payment_allocations` allows INSERT/UPDATE/DELETE whenever `payments.status <> 'cancelled'`, so posted receipts qualify. Restrict the three write policies to `payments.status = 'draft'`. First `grep` the app for any screen or action that writes allocations of a **posted** payment (the audit trigger has `reallocate`/`unallocate` actions, so it may be intended); if one exists, stop and ask Ratna. Otherwise re-allocation of a posted receipt is a later change done through a function that reverses and re-applies with an audit row. `cancel_document` is SECURITY DEFINER and must keep working.
3. **L1 + F4 — nothing guards the catalog (medium, latent) and one function is open to signed-out callers (low).**
   - `revoke execute on function public.gstin_checksum_ok(text) from public, anon;` (keep `authenticated`, `service_role`).
   - `alter default privileges in schema public revoke execute on functions from anon;` — the schema-scoped default ACL currently hands every new function to `anon`. (A schema-scoped revoke only subtracts from the schema-scoped entry; verify by creating a function inside a rolled-back transaction, as the report did.)
   - New pgTAP guard in the new test file, catalog-wide, so Phase 2 cannot regress it: (a) no function in `public` is executable by `anon`; (b) every table in `public` has `relrowsecurity` on; (c) every view is `security_invoker`; (d) no table in `public` grants any privilege to `anon`. List the exceptions explicitly if any exist (there should be none).
   - Event trigger that auto-enables RLS on new `public` tables: try it locally, but do **not** assume hosted `postgres` may create event triggers — if unsure, skip it, keep the pgTAP guard, and note it in `implementation-notes.md`. Do not change `authenticated`'s table default privileges (the explicit-grants migration already states the real grants).
4. **F3 — `created_by` can be forged (low).** BEFORE INSERT/UPDATE trigger on every document header table that has `created_by`: for an app session (`auth.uid() is not null`) set `created_by := auth.uid()` on insert and keep `old.created_by` on update. Seeds and `service_role` (no `auth.uid()`) unchanged.
5. **F5 — no-one identities can still call helpers (low).** `hidden_payroll_entry_ids()` / `hidden_payroll_voucher_ids()` return nothing when `current_app_role() is null` (aal1 admin, deactivated user); they must keep returning the ids for `user` and nothing for `admin` (the RLS policies depend on both). `set_my_locale(text)` writes only when `current_app_role() is not null`.
6. **Tests.** New `supabase/tests/database/000NN_attack_test_fixes.test.sql` (next free number): a raise or empty result for each of F1–F5, with the owner and counter positive cases still passing (`post_sales_invoice` for a normal in-state and an inter-state invoice; a draft receipt's allocations still editable by both roles; `cancel_document` on a receipt with allocations still works). Plus the catalog guards from item 3.
7. **Harness expectations.** Flip the expectations that encode today's behaviour, so the next run of `scripts/attack-test/run-all.sh` shows zero FAIL rows: `matrix.mjs` (allocations of a posted receipt: user INSERT/UPDATE/DELETE), `tamper.mjs` (B1, B1b, B1c, B3b), `funcs.mjs` / `extras.mjs` (F4 anon `gstin_checksum_ok`, F5). Do not weaken any other expectation.
8. **Docs.** `db-architecture` (allocations immutable after posting; place of supply = delivery state, validated; catalog invariants), `docs/STATUS.md`, and a "closed" note on the report.
