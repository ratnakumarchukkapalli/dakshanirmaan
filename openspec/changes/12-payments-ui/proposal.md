## Schema addition (small, read-only — needs Ratna's go-ahead before this change is built)
`v_open_sales_invoices` (change 06) has no mirror for purchase invoices, because purchase-invoice creation has no UI until change 21. But `post_payment` already supports `direction = 'payment'` against `purchase_invoices`, and the allocation grid needs a source for those rows too, or outgoing payments can never show what they're settling. One new migration:
- `v_open_purchase_invoices` — exact mirror of `v_open_sales_invoices` (change 06's own migration), same `open_amount` formula (`grand_total − Σ allocations of posted payments − Σ posted debit_notes`), same `WHERE open_amount > 0`, reading `purchase_invoices` + `debit_notes` instead of `sales_invoices` + `credit_notes`. No `interest_rate_pm`/age-based interest column — that feature (`v_party_interest`) is customer-only in the spec, nothing charges *us* overdue interest.
One pgTAP test file mirroring `00016_challan_invoice_unique_draft.test.sql`'s style: seeds a purchase invoice with and without allocations/debit notes, asserts the view includes/excludes it correctly.

## Scope

**In**
1. **Payments list** `/payments`: tiles (Received today, Cheques in hand / PDC, Cheques issued, Unallocated on account) computed from `payments` + `payment_allocations` directly (simple SUMs over already-posted amounts — display aggregation, not new financial truth, same category as the sales list's stored `grand_total`). Table: Voucher (mode as a `sub`), Party, Mode/reference (cheque no + bank, or UPI/NEFT ref), Amount (right, tabular), Allocated (doc references it settled, or "On account"), Status chip (draft / posted / cheque sub-states — in hand, deposited, cleared, bounced, issued, presented / cancelled). Segmented **All / Receipts / Payments / Drafts** (mirrors the sales/challans list convention), search by voucher number or party name (reuse `src/lib/search.ts`). A draft row opens the form (`?id=`); a posted cheque receipt row that is still `in_hand` or `deposited` shows inline **Deposit** / **Mark cleared** buttons (member); a `user`-role account sees no **Bounce** button (admin only, per the DB gate) — same "the UI shows only what the database will accept" rule as change 10's cancel button.
2. **Payment form** `/payments/new` (and `?id=` to resume a draft — no separate `[id]/` route, matching the frontend spec's route tree and change 11's challan precedent): a **direction toggle** (Receive / Pay) that is receipt-only for a `user`-role account (the DB refuses `direction = 'payment'` posting from anything but admin — the toggle is hidden, not just disabled, for a counter-staff session) and switches the party picker between customer/both and supplier/both. Party, date (default today, future refused), amount, mode (cash/UPI/NEFT/cheque/bank), account (money accounts only, same `is_money` filter change 10 already uses), reference/UTR, cheque fields (instrument no. required by the DB when mode is cheque, instrument date, bank — shown only for `mode = 'cheque'`), a note. **Discount** field is admin-only (rendered only for a verified admin session, mirroring change 10's credit-override pattern) because posting with `discount > 0` is admin-only in the database.
3. **Allocation grid**: once a party is chosen, lists that party's open invoices (sales invoices for a receipt, purchase invoices for a payment — from `v_open_sales_invoices` / the new `v_open_purchase_invoices`, both preloaded for every party up front in the page's server loader, same "everything to pick from, loaded once" pattern as the challan/invoice forms — no per-keystroke client fetch). Each row: document ref + age, open amount, an editable allocate-amount input capped client-side at that row's open amount (display only — `post_payment` re-validates every cap under the row lock at post time and is the actual authority). A progress bar and "X unallocated" / "Fully allocated" summary (exact-decimal, never `Number`). **Auto-allocate oldest first** fills rows by ascending `age_days` until the payment amount is exhausted; **Clear** zeroes every row. Below 600px the Due column collapses into the row's sub-line (prototype's `.mdue`), matching the CSS already specced (`.tiles`/`.tile`/`.alloc`/`.progress` — none of these exist in `globals.css` yet; port them from the prototype's `<style>` block verbatim, same tokens).
4. **Actions** `src/app/actions/payments.ts` (envelope + role gate + revalidate, `requireMember`/`requireAdmin` from `src/lib/auth/require.ts`, same shape as `challans.ts`): `saveDraftPayment` (insert-or-update header + delete-and-reinsert `payment_allocations` in one call, stale `updated_at` → `conflict`, same pattern as `saveDraftChallan`'s line replacement), `postPayment` (`post_payment`; reads the draft's `direction`/`discount` first and requires a verified admin session when `direction = 'payment'` or `discount > 0`, mirroring `postInvoice`'s `overrideCredit` gate — the database independently re-checks both), `depositCheque` (`deposit_cheque`, member), `markCleared` (`mark_cheque_cleared`, member), `bounceCheque` (`bounce_cheque(id, reason)`, admin, `reason` a required short text in a confirm modal). Map `DN_CHEQUE_STATE` → a new `cheque_state` error code (`ErrorCode` union + `DB_CODES` in `src/lib/action-result.ts`; the api spec already names this code as "added" and unmapped) and the `DN_VALIDATION:*` details this feature introduces (`invalid_amount`, `invalid_discount`, `invalid_account`, `cheque_details`, `allocation_exceeds_payment`, `allocation_invoice_not_posted`, `allocation_party_mismatch`, `allocation_exceeds_invoice`, `missing_account`) in en + te.
5. English and Telugu strings for everything; both themes; 390 px; keyboard: Enter on list rows, focus order sensible, Escape closes dialogs/the bounce-reason modal; `Field` for every input.
6. Tests: Vitest for the allocation-cap math (client-side capping + auto-allocate-oldest logic, exact decimal, no floats), the action envelope (ok / forbidden / a `DN_*` mapping / stale conflict / the new admin gates for outgoing-payment and discount posting), search escaping (reuse existing harness). pgTAP for `v_open_purchase_invoices` only (see "Schema addition"); no other database change is expected. A real-browser walk-through once local Supabase is running, same discipline as change 11's follow-up — a receipt, a cash deposit → clear cycle, and one bounce, watched end to end against a live database before this is called done.

**Out (log in notes)**: bank reconciliation / CSV import (`payments/reconcile/`, change 22); purchase-invoice creation (change 21 — the allocation grid only reads what already exists, seeded or entered directly); credit/debit notes UI (their tables already feed the open-amount formulas; the note *screens* are later changes); price/rate anything (payments carry no tax); a payment against a bank statement line (change 22); editing a posted payment (never — the cheque-lifecycle functions and `cancel_document` are the only transitions the database allows).

## Conservative defaults (owner unknowns — log each in `implementation-notes.md`)
1. Any active member can create, edit, save-draft and post a **receipt**; only a verified admin can post an outgoing **payment** or any payment carrying a discount — read directly off `post_payment`'s own role gate, not a guess.
2. Deposit and mark-cleared are member actions (moves money between our own accounts, or changes a status only); bounce is admin-only — read directly off `deposit_cheque`/`mark_cheque_cleared`/`bounce_cheque`'s own role gates.
3. No dedicated view screen for a posted payment, same reasoning as change 11's challans: the frontend spec's route tree lists only `payments/new/` (and `reconcile/`, out of scope) for this section. The list row carries everything (status chip, inline cheque actions).
4. No `deleteDraftPayment` action — the api spec's `payments.ts` row names exactly `saveDraftPayment`/`postPayment`, plus the three cheque-lifecycle extensions. An unwanted draft is left unposted, same as challans.
5. `v_open_purchase_invoices` carries no interest/ageing-bucket columns — nothing in the spec charges the business overdue interest on its own payables; only `v_party_interest` (customer-side) exists.
6. The bounce-reason text has no format requirement beyond "not empty" — the database takes free text.

## Done when
- **"allocation cap + auto-allocate"**: typing more than an open invoice's due amount into its allocation input is clamped to that invoice's open amount on the spot; "Auto-allocate oldest first" fills the oldest open invoices first up to the payment amount and leaves the remainder unallocated; posting re-validates every cap against the live database regardless of what the form displayed (tamper test: edit an allocation past the cap in dev tools, post, and the database's own re-validation is what actually decides — plus a parity test that a normal allocation the UI would never let through fails the same way if forced).
- **"bounce flow"**: depositing a cheque receipt moves it from "in hand" to "deposited" (Dr bank / Cr cheques-in-hand shown in the resulting journal, read from the existing views); marking it cleared is a status change only; bouncing (admin) reverses the original receipt (and the deposit, if one happened), deletes its allocations, and the invoices it had settled show open again in the party's aging — verified live, not just asserted from notes.
