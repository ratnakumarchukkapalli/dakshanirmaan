## Scope (10b)

**In**
1. **PDF route** `GET /api/invoices/[id]/pdf` (`runtime = 'nodejs'`, `@react-pdf/renderer`, user-scoped client so RLS decides): posted and cancelled invoices only (a draft returns 409 with a plain message; unknown id 404; not signed in 401). Filename `DN-<number with "/" → "-">.pdf`, e.g. `DN-26-27-0001.pdf`. Content, English (Rupee sign needs a bundled font: an OFL font file under `src/assets/fonts/`, licence noted): organisation legal name, GSTIN, address, "Tax Invoice"; number, date, place of supply; bill-to and ship-to **from the invoice snapshots**; party GSTIN; vehicle / transporter / EWB number when present; lines from `sales_invoice_lines` snapshot columns only; stored CGST/SGST or IGST, round-off, grand total; **amount in words**; bank details, footer text and UPI QR from the organisation row; "for <legal name>, authorised signatory". A **cancelled** invoice is rendered with a large CANCELLED watermark and no QR. Multi-page safe (repeat table header, keep totals together).
2. **Amount in words** in `src/lib/format.ts`: Indian system (Lakh / Crore), whole rupees plus paise ("Rupees Twelve Thousand Five Hundred and Forty Paise Only"), exact from the stored decimal string (no floats). Golden-table vitest.
3. **UPI QR** on the PDF: `qrcode` package, server side, `upi://pay?pa=<vpa>&pn=<legal name>&am=<open amount>&tn=<invoice no>&cu=INR`. Shown only when the organisation has a UPI ID, the invoice is posted (not cancelled) and there is an open amount (grand total minus posted receipts allocated to it; if nothing is owed the PDF says "Paid" and shows no QR). On the invoice form's totals panel a one-line note: "The printed invoice carries a UPI QR" or, when no UPI ID is set, "No UPI ID set — an owner can add it in Settings → Organisation".
4. **WhatsApp share**: `src/app/actions/share.ts` → `whatsappInvoiceLink(invoiceId)`. Any active member. Builds a `https://wa.me/91<mobile>?text=…` link (mobile = party `whatsapp_phone`, else `phone`, through `src/lib/phone.ts`; no usable number → a friendly refusal, and the button offers "Copy link" instead). The text carries the invoice number, date, amount, trade name and a **signed, 24-hour link** to the PDF. Signing: HMAC-SHA256 over `<invoiceId>.<expiry>` with a server-only secret `INVOICE_LINK_SECRET` (≥ 32 chars; missing → the action refuses, it never falls back to an unsigned link). The same PDF route accepts `?exp=&sig=` instead of a session: the signature is checked first (constant-time), then the invoice is read with the **service client for that one invoice id only**; expired / bad signature → 403 with no detail; per-IP rate limit reusing `src/lib/auth/rate-limit.ts`. `src/lib/access.ts` learns one exact public exception for that path shape, unit-tested so no other `/api` path becomes public. The link origin comes from `APP_ORIGIN` (server-only) with the request host as a development fallback.
5. **Print**: a **Print** button opens the PDF in a new tab (the PDF is the one layout truth); plus a small `@media print` block so printing the posted view itself hides the shell and buttons.
6. **EWB / transport panel**: fields transport mode (road / rail / air / ship), distance (km), transporter name, transporter GSTIN (validated), vehicle number, and **e-way bill number (12 digits), date, valid-until**. Before posting these live in the draft form (collapsed "Transport and e-way bill", extends the existing vehicle/transporter disclosure) and are saved with the draft. The e-way bill itself is generated on the government portal by the family and typed here — there is **no portal integration** (Phase 3). After posting the panel is edited on the posted view through a new database function (see Migration). A hint (not a block) appears when the grand total is above ₹50,000 and no EWB number is recorded: "An e-way bill is usually needed for goods worth more than ₹50,000 moved by road — verify with your CA / the portal"; the threshold is one named constant in `src/lib/gst.ts`.
7. **Buttons** on the posted view header: PDF, Print, WhatsApp (not on cancelled invoices except PDF). Draft pages show none of them. English + Telugu UI strings for everything except the PDF body (English by spec); both themes; 390 px; tap targets ≥ 44 px; Escape closes dialogs.
8. **Tests**: Vitest for amount in words, link signing (valid / expired / tampered id / tampered expiry / wrong secret), the `access.ts` exception (exactly one shape public), the share action envelope (ok / forbidden / no phone / missing secret), the EWB action (ok / bad number / forbidden / DB refusal), and a PDF render smoke (bytes start `%PDF`, page count, cancelled variant differs). **Visual check**: render PDFs for a 1-line intra-state cash sale, a 12-line inter-state credit sale (multi-page), and a cancelled invoice, rasterise with `pdftoppm`, and inspect the images. Real-browser walk-through at 1280 and 390 px.

**Migration (one, additive, new file `supabase/migrations/20260920140000_invoice_ewb.sql`)**: `record_invoice_ewb(...)` — `SECURITY DEFINER`, `set search_path = ''`, active member only, invoice must be `posted` (not draft, not cancelled), sets **only** the transport and EWB columns of `sales_invoices` (never money, party, lines, status), checks (`ewb_no ~ '^[0-9]{12}$'`, GSTIN shape, mode in the four values, distance ≥ 0, valid-until ≥ date), writes an `audit_log` row with old and new values, `execute` granted to `authenticated` only. pgTAP `00013_invoice_ewb.sql`: happy path, draft refused, cancelled refused, counter user allowed, anon refused, money columns unchanged, audit row present, bad EWB number refused. This is the only way a posted invoice's row changes; the RLS policy "update only while draft" stays exactly as it is.

**Out (log in notes)**: challan PDF and "against challan" (change 11); e-invoice IRN / signed QR (Phase 3); EWB / IRN portal APIs; Telugu PDF; HSN-wise tax summary table (Phase 2, GSTR-1 change 18 needs it — note it); credit-note PDF; a cancel-receipt path for cash sales (payments change) and the `save_sales_draft` RPC and `ship_to_address_id` column noted in 10a (not needed here); emailing invoices; bulk PDF.

## Conservative defaults (owner unknowns — log each in `implementation-notes.md`)
1. Any active member may download / print / WhatsApp an invoice and record its EWB details; nothing here changes the books, so it is not owner-gated. **Owner question: should counter staff be able to send invoices on WhatsApp?**
2. The WhatsApp link expires in 24 hours (spec); the customer sees the invoice as it was at the time of opening, including a CANCELLED watermark if it was cancelled since. **Owner question: is a link that shows the customer's invoice to anyone who forwards it acceptable for 24 hours?**
3. The UPI QR amount is the open amount at the time the PDF is made, not the full total, so a part-paid invoice never asks the customer to pay twice.
4. A PDF is generated on request and never stored (no Storage bucket, nothing to leak or clean up).
5. The e-way-bill threshold hint is advice, never a block.
6. Invoice PDFs are English only; item names print as snapshotted.
